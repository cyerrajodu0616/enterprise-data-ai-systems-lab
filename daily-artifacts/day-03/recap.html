Core habit

Stop, Assess, Then Answer

Physical layout is a conditional decision. Preserve what is known, expose missing evidence, and validate the causal bottleneck.

Observation→Known→Assumption→Missing evidence→Inspect→Conditional change→Validate
August 2026: learner answer and refinement

Scenario: hypothetical 5B-row ORDERS table across ten years, monthly partitioned on order_date.

My reasoning: an August 2026 query should not scan all rows when the predicate aligns with the partition key.

Refinement: the optimizer may prune irrelevant partitions only when predicate form and engine behavior permit safe elimination. Partitioning is not a scan-reduction guarantee.

Workload before layout

For hypothetical 70% recent, 15% two-year customer, 10% product/date, and 5% other queries, date is an important coarse-elimination candidate—not a final decision. Ask for predicate combinations, correlation, selectivity, cardinality, distribution, skew, and current scan behavior.

Mental model

Pruning, Skipping, Filtering—and Three Physical Layers

Partition pruning→Data skipping→Predicate filtering

Pruning eliminates coarse partitions. File/row-group statistics can skip candidates that cannot match. Filtering evaluates what remains. Skipping identifies what can safely be avoided; it does not necessarily locate an exact row.

Index analogy: where it breaks

My initial mapping: use a database index for customer_id = 12345.

Refinement: an optimizer chooses index access from selectivity, statistics, structure, locality, and cost. B-tree lookup is not file-statistics skipping, and statistics may eliminate a file without identifying the matching row.

Locality and UUID correction

Random IDs scattered across every file can create broad/overlapping ranges and weak skipping. UUIDs are not inherently unsuitable: deterministic ordering plus physical locality can make statistics selective. Trace locality → metadata selectivity → skipping effectiveness.

Important: small files can increase metadata, file-open, planning, and scheduling overhead. They do not inherently cause shuffle; redistribution requirements cause shuffle.

Falsifiers: downstream shuffle, spill/GC, skewed stragglers, scan growth, pruning regression, or another stage dominates.

Remediation versus prevention

Compact/rewrite stored small files; do not use repartition() as a synonym. A 20 MB batch cannot independently produce 128 MB of data. Evaluate freshness outcome → cadence → file behavior → maintenance cost, preserving a justified SLA.

Predicate shape

Do not say YEAR(order_date) always prevents pruning. Inspect plan, partition filters, pushed filters, selected partitions/files, and bytes scanned for the actual engine/version.

Regression ladder

  1. Acknowledge Known facts, including unchanged code.
  2. Inspect source behavior, plan, filters, partitions, and files.
  3. Compare bytes/task, duration distribution, shuffle, spill, and stage time.
  4. Separate scan/layout from runtime distribution.
  5. Use repartition() only for a demonstrated distribution/parallelism problem.
  6. Validate equivalent results, then causal performance metrics.
Final Architect/Engineer challenge

Known: hypothetical 5B rows; day/country/product-category layout; ~3M files, many under 5 MB; rare product-category filters; scattered customer IDs; 15-minute ingestion; unverified 20-minute SLA.

Missing: fragmentation cause, pruning/skipping selectivity, latency stage, skew, SLA outcome.

Candidates—not decisions: simplify low-value partition dimensions, improve customer locality, compact history, and prevent recurrence while preserving justified freshness.

Validate: correctness first, then partitions → files → bytes → tasks → duration → stage/runtime.

Evolving layout

Liquid Clustering from Fundamentals

Clustering asks which values need better locality so metadata can eliminate more irrelevant data.

Workload→Predicates + combinations→Selectivity + distribution→Current skipping→Cost→Measure

Frequency alone is insufficient; selectivity alone is insufficient. Databricks documentation checked 2026-09-03 states that changing keys affects subsequent writes and OPTIMIZE but does not automatically rewrite existing data. Consider historical range, old-layout performance, business requirement, and rewrite/reclustering cost separately.

Principle: Flexibility in physical organization does not eliminate migration cost; it changes how migration can be managed.

Practice: “A partitioned table became much slower. How would you diagnose it?”

I start with expected correctness and dominant access patterns. I inspect the plan, partition filters, selected partitions, files considered/skipped/read, bytes scanned, tasks, bytes per task, duration distribution, and stage timing. That separates coarse pruning, file skipping, file-management overhead, and runtime redistribution. Similar bytes with vastly more files/tasks supports a small-file hypothesis, while shuffle, spill, skew, scan growth, or another stage could falsify it. I compact stored files and use repartition only for demonstrated runtime distribution problems. Layout or clustering changes remain conditional on current locality, maintenance cost, and historical access. I validate equivalent results first, then the intended causal bottleneck.
