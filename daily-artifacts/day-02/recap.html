Core habit

Stop, Assess, Then Answer

Never silently convert an unknown into a fact. Precise uncertainty is stronger than a vague “it depends.”

Observation→Known→Assumption→Missing evidence→Inspect / ask→Conditional diagnosis→Recommendation→Validate
Reusable Staff-level response

“I do not have enough information to choose yet. I would check X and Y because they determine Z. If X is true, I would choose A; otherwise I would investigate B. I would validate with …”

Broadcast decision

Weak: “CUSTOMERS has 5M rows, so broadcast it.”

Known: 5M rows. Missing: projected bytes, in-memory hash representation, worker memory, estimates/configuration.

Better: If the projected build side is safe and economical to distribute and hash, Broadcast Hash Join is an initial candidate.

Slow executor

Weak: “One executor is slow, so we have skew.”

Inspect task duration, shuffle read, partition size, key frequency, spill, and memory. One/few outlier tasks support a hot-key hypothesis.

Add executors

Weak: “The job is slow, so add executors.”

Distinguish insufficient aggregate capacity from an indivisible skewed partition. More capacity does not split one hot key.

Increase partitions

Weak: “Increase shuffle partitions to fix the large task.”

Uniformly large partitions may benefit; one hot hash key remains together under normal partitioning.

Output explosion

Weak: “Spark produces too many rows.”

Compare expected N:1 with actual N:M using per-key counts before tuning.

Duplicate customers

Weak: “Deduplicate CUSTOMERS.”

Establish why the invariant failed and select the valid record using defined semantics.

Broadcast disappeared

Weak: “Force broadcast.”

Compare projected size, filters/projection, estimates/statistics, and configuration across good and bad runs first.

Traditional selection reasoning

Scenario: conceptual ORDERS 1B, CUSTOMERS 5M, no indexes or ordering. The learner correctly considered projected size, memory, and prerequisite work and initially preferred hash join.

Refinement: indexed nested loop may be reasonable; hash representation can exceed serialized size; sort-merge can spill and becomes attractive when ordering exists.

Principle: Ask which expensive prerequisite work has already been done.

Hash partitioning co-locates equal keys but does not order rows inside partitions.

Reduce data before movement

Projection: conceptual CUSTOMERS grew from about 150 MB to 6 GB with the same row count. Selecting two required attributes may change the physical strategy, not just runtime. SELECT * can remove broadcast and make the replacement shuffle move wider rows.

Filtering: business requirement → filter → project → re-evaluate size → choose strategy. Source predicate pushdown and a Spark Filter before Exchange are distinct; ask where the physical plan actually reduced data.

Production reasoning

Skew, Cardinality, AQE, and Salting

Skew

Most partitions similar; one/few outliers. Say: “a straggler task is processing a disproportionately large shuffle partition.”

Generally oversized

Most/all partitions similarly large. Additional partition-level parallelism may help.

Why executors and normal shuffle partitions may not fix HOT

Additional executors add capacity but do not split one hash key. Moving/retrying the task changes placement, not distribution. Changing 200 to 2000 normal shuffle partitions still maps all hash(HOT) records together.

Selective salting and correctness
Fact: HOT→HOT,0 · HOT,1 · HOT,2
Dimension: HOT→ replicateHOT,0 · HOT,1 · HOT,2

Join on (customer_id, salt). If only the fact is salted, matches are lost. Replication amplifies the other side. Choose buckets from measured hot volume, task health, memory/spill, slots, overhead, and amplification—not executor multiples. Perfect slot use is not minimum runtime.

AQE before manual salting

AQE means Adaptive Query Execution. It can use runtime shuffle statistics to identify outlier partitions without knowing the business identity HOT. AQE skew handling is not automatic salting.

Reduce data→Simplest valid join→Verify skew→AQE→Manual salting if required
Cardinality: correctness before tuning

Output(K) = LeftCount(K) × RightCount(K)

3 × 3 = 9. The conceptual 10M HOT × 500K HOT example implies five trillion logical rows; it is arithmetic, not a measured run. Input skew concerns distribution; cardinality explosion concerns multiplicative matches.

Expected SALES N:1 CUSTOMERS, but C999 has 25 active records: investigate the violated invariant, identify the valid record from defined rules, restore N:1, validate, rerun/measure, then consider legitimate skew. Source, ingestion, CDC, SCD, and active-record logic are investigation areas—not asserted causes.

Do not salt your way around incorrect business data.

Plan regression: Broadcast yesterday, Sort-Merge today
  1. Did actual projected build-side volume/width change?
  2. Did environment/configuration change?
  3. Are estimates/statistics missing or wrong?
  4. Did projection change?
  5. Did selectivity or early reduction change?

Distinguish actual size from optimizer-estimated size before forcing a plan.

Debugging ladder

  1. What changed?
  2. Is expected versus actual cardinality correct?
  3. Are filters and projections minimal and early?
  4. Which physical plan was selected, and why?
  5. Where does data move?
  6. What do task/partition metrics show?
  7. Generally oversized partitions or skew?
  8. Can AQE handle verified skew?
  9. Only then consider manual salting.

Practice: “A Spark join became much slower. How would you diagnose it?”

I start by asking what changed and validating expected versus actual join cardinality, because N:1 becoming N:M is a correctness problem that tuning can mask. Then I verify filters and projections are minimal and early, inspect the physical plan, and explain why Spark selected its strategy using projected size, estimates, and configuration. I locate Exchanges, Sorts, and BroadcastExchange, then inspect task duration, shuffle read, partition size, spill, and key-frequency distributions. That distinguishes generally oversized partitions from hot-key skew. I prefer the simplest correction—restore cardinality, reduce data, or recover a valid broadcast path—then evaluate AQE. I use selective salting only when evidence still justifies it, preserving join correctness and measuring replication cost.

Amex STAR story

Situation: A growing Amex join workload initially completed with available Spark resources. Task: Investigate why continued growth caused OOM around the third month. Action: Investigation found an effective N×N/cardinality explosion. Lesson: Resource capacity can temporarily mask multiplicative semantic defects. No additional scale, date, implementation, or business metric is claimed.
