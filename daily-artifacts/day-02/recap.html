Stop, Assess, Then Answer

This is the central Day 2 upgrade: do not silently convert an unknown into a fact.

Observation → Known → Assumption → Missing Evidence → What to inspect / ask → Conditional diagnosis → Recommendation → How to validate

“I do not have enough information to choose yet. I would check X and Y because they determine Z. If X is true, I would choose A; otherwise I would investigate B. I would validate with …”

Broadcast decision

Weak: “CUSTOMERS has 5M rows, so broadcast it.”

Known: 5M rows. Missing: projected bytes after filter/projection, hashed in-memory representation, worker memory, statistics/configuration.

Conditional answer: If the projected build side is safe and economical to distribute and hash, Broadcast Hash Join is an initial candidate.

Slow executor

Weak: “One executor is slow, so we have skew.”

Inspect task-duration, shuffle-read, partition-size, key-frequency, spill, and memory distributions. If one/few tasks process outlier partitions, investigate hot keys.

Add executors

Weak: “The job is slow, so add executors.”

First distinguish insufficient aggregate capacity from an indivisible skewed partition. More capacity does not inherently split one hot-key partition.

Increase partitions

Weak: “Increase shuffle partitions to fix the large task.”

If most partitions are large, additional partition-level parallelism may help. If one key dominates, normal hash partition count does not inherently split it.

Output explosion

Weak: “Spark produces too many rows.”

Ask expected cardinality. Compare expected N:1 with actual N:M using per-key counts before tuning.

Duplicate customers

Weak: “Deduplicate CUSTOMERS.”

Establish why the uniqueness invariant failed and identify the valid record from defined semantics. Arbitrary deduplication can hide the defect.

Broadcast disappeared

Weak: “Force broadcast.”

Compare actual projected build size, filter/projection, optimizer estimates/statistics, and configuration across good and bad runs. If growth is legitimate, forcing broadcast treats the symptom.

Traditional Join Selection

Scenario / question

Conceptual ORDERS = 1B rows; CUSTOMERS = 5M; no indexes; neither sorted.

My reasoning

Row counts alone were insufficient. Projected size and compute/memory matter. Hash join looked attractive; nested loop suggested repeated access; sort-merge introduced sort CPU, memory, and I/O.

What was correct

The reasoning compared prerequisite work and identified the smaller build side.

Correction / refinement

Join algorithm and access path belong together. Indexed/selective nested loop can be reasonable. Hash representation can exceed serialized size. Sort-merge can spill and becomes more attractive when ordering already exists.

Staff/Lead vocabulary

“Do not only ask which algorithm is cheaper. Ask which expensive prerequisite work has already been done.”

Interview version

“I would compare projected bytes, access paths, ordering, selectivity, and memory. With no useful access path or order, hash join is a candidate—but I would not select from row count alone.”

Broadcast Hash Join: Build and Probe

Scenario: Conceptual ORDERS = 1 TB; CUSTOMERS initially small.

My reasoning: Broadcast the smaller customer relation to avoid redistributing the 1 TB fact.

Correct: CUSTOMERS is the build side; ORDERS is the probe side. Probe rows can be processed against the hash structure; the whole probe need not fit in memory. Broadcast still pays for BroadcastExchange.

Refinement: serialized/on-disk size ≠ in-memory hash-table size. Include replication, network, execution memory, concurrent workload, and overhead. Build keys need not be unique; duplicates produce multiple matches—no “latest wins.”

Sort-Merge Join pays for ordering so it can merge. Hash Join pays for a hash structure so it can probe.

Reduce Data Before Optimizing Movement

Projection

In the conceptual scenario, CUSTOMERS widened from roughly 150 MB to 6 GB with the same row count. The learner proposed selecting only two required attributes and reassessing strategy.

Correct: row count ≠ data size. Projection can make broadcast feasible, changing strategy rather than merely improving it slightly.

Double regression from SELECT *: the build side stops being attractive for broadcast; the replacement shuffle join now scans, serializes, moves, sorts, spills, and emits wider rows.

Filtering

For NJ/active customers: business requirement → filter → project → re-evaluate size → choose strategy

Predicate pushdown

Source pushdown can avoid reading irrelevant data. Even without it, Spark Filter before Exchange/join can reduce work. Ask: “At what point in the physical plan was data actually reduced?”

Sort-Merge Join Internals

Left Scan → Exchange hashpartitioning(key) → Sort ↘
Right Scan → Exchange hashpartitioning(key) → Sort → SortMergeJoin

One logical redistribution requirement appears as Exchange/shuffle on both inputs. Exchange solves location. Matching keys reach corresponding partitions. Sort solves ordering. Hash partitioning does not order rows within a partition.

Skew, Executors, and Shuffle Partitions

Scenario: One conceptual hot customer is about 35% of one side.

My reasoning: One task takes much longer; adding executors does not split the hot key because equal hash keys still route together.

Correction: Say “a straggler task is processing a disproportionately large shuffle partition,” not “one executor is slow.” A slow executor alone is not proof.

Diagnose at task/partition level before blaming an executor.

Selective Salting

My reasoning: Salt only HOT as (HOT,0), (HOT,1)… so it can reach multiple partitions/tasks.

Correctness challenge: If only the fact is salted, matches are lost. For N:1, replicate the matching dimension row across identical salt values, then join on (customer_id, salt).

Cost: Replication amplifies the other side; many matching HOT rows multiplied across many buckets can be enormous.

Bucket correction: Do not choose an executor multiple. Use measured hot volume, unsalted partition behavior, healthy task evidence, memory/spill, execution slots, scheduling overhead, replication, and remeasurement. Perfect slot utilization ≠ minimum runtime.

AQE and Plan Regression

AQE is Adaptive Query Execution. Static optimization asks what is expected; adaptive execution asks what actually emerged after a stage and whether physical execution should adjust. Outlier shuffle statistics can support skew handling without semantic knowledge of HOT. AQE is not automatic salting.

reduce unnecessary data → simplest valid join → accept legitimate shuffle → verify skew → investigate AQE → selective salting only if required

Broadcast yesterday, Sort-Merge today

  1. Actual projected build-side volume/width?
  2. Environment/configuration?
  3. Statistics/estimates?
  4. Projection change?
  5. Filter selectivity/early reduction change?

Distinguish actual relation size from optimizer-estimated size. Bad estimates can produce a poor initial plan.

Join Cardinality: Correctness Before Tuning

Output(K) = LeftCount(K) × RightCount(K)

Three left rows × three right rows = nine output rows. The conceptual 10M HOT × 500K HOT example implies five trillion logical rows; it is arithmetic, not a measured run.

Input skew concerns disproportionate input distribution. Cardinality explosion concerns multiplicative matches. The engine may be correctly executing incorrect business semantics.

Expected SALES N:1 CUSTOMERS; C999 has 25 active customer rows

  1. Investigate why the business uniqueness invariant failed.
  2. Determine the valid record from defined business/version rules.
  3. Restore N:1 and validate the key.
  4. Rerun and measure a representative workload.
  5. Only then investigate legitimate hot-key skew/AQE.

Source, ingestion, CDC, SCD/versioning, and active-record logic are possible investigation areas—not asserted causes.

Do not salt your way around incorrect business data.

Learner Production Experience: Amex

A prior Amex join was effectively N×N. Available Spark resources initially processed the growing workload. Around the third month, continued growth caused OOM. Investigation found the N×N/cardinality explosion.

Lesson: Resource capacity can temporarily mask a cardinality defect; multiplicative output eventually overwhelms the system. No additional scale, date, implementation, or business metric is claimed.
